# AGENTS.md

Инструкции по работе агента в frontend-проекте `shortcut-chat/client-ng`.

Структура приведена в соответствие с глобальной `documentation-governance.md`. Нормы — в `.agents/rules/`, требования — в `openspec/specs/`, карта системы — в `.agents/context/frontend.md`.

## Порядок чтения

1. Учти уже загруженные Global Rules и этот `AGENTS.md`.
2. Определи тип работы и выполни обязательный порядок из матрицы до предметного анализа.

| Тип работы | Обязательный порядок до предметного анализа |
|---|---|
| Архитектурный анализ | Загрузить соответствующий Skill → прочитать `.agents/context/frontend.md` → прочитать `.agents/rules/architecture/index.md` → открыть релевантные Rules и Specs → изучить код |
| Планирование и реализация frontend | Загрузить `senior-frontend-developer` → прочитать `.agents/context/frontend.md` → прочитать `.agents/rules/development/index.md` → при затрагивании архитектуры или API прочитать `.agents/rules/architecture/index.md` → открыть релевантные Rules и Specs → изучить код |
| QA и проектирование тестов | Загрузить `qa-engineer` → прочитать `.agents/context/frontend.md` → прочитать `.agents/rules/testing/index.md` → открыть релевантные правила и `.agents/procedures/verification.md` → изучить тестируемый код |

Правила применения:

- Глобальная загрузочная инструкция `caveman-global-dev.md` остаётся отдельной и не входит в маршрутизацию этого раздела.
- До исследования кода выполни требуемые вызовы `skill` и прочитай обязательные источники для своего типа задачи.
- Если путь отсутствует или файл не удаётся прочитать, сообщи об этом и не утверждай, что требование выполнено.
- Чтение тематического индекса не заменяет чтения самих Rules, необходимых для конкретной задачи.
- Не читай несвязанные тематические индексы.
- Для составной задачи применяй требования каждого действительно задействованного типа работы.
- Не меняй Specs, Rules приложения или техническую реализацию в рамках анализа и планирования.
- Для обычных вопросов и задач вне матрицы читай только релевантные источники; общий `.agents/rules/index.md` используй как маршрутизатор.

Не читай все документы заранее. Выбирай по области задачи. Требования функции ищи в задаче или Spec, не выводи из Rules. Если сомневаешься, применим ли документ, прочитай его.

## Источники истины

- Нормы и ограничения — `.agents/rules/`.
- Согласованные требования — `openspec/specs/`; серверные API-контракты — backend Specs.
- Текущая карта frontend — `.agents/context/frontend.md`.
- Стек, сборка и зависимости — `package.json`, `package-lock.json`, `angular.json`, `tsconfig*.json`.
- Фактическое поведение — `src/**` и тесты.
- Проверка изменений — `.agents/procedures/verification.md`.

## Расхождения

- Rule — ограничение для агента.
- Spec — ожидаемое поведение системы.
- Domain Profile — справочная карта текущего состояния.
- Код и тесты — свидетельство фактической реализации.

При конфликте Rules, Specs и кода остановись, зафиксируй источники и точные формулировки, опиши последствия вариантов и запроси решение. Не выбирай сторону молча и не объявляй текущее поведение кода новым требованием.

## Порядок работы

1. Исследуй задачу, затронутый код и применимые источники.
2. Составь план: файлы, операции, порядок, риски, проверки.
3. Запроси подтверждение по глобальному `confirmation.md`; жди явного согласия.
4. Реализуй только согласованный объём.
5. Перед сборкой, тестами, запуском приложения, миграциями и git-мутациями запроси отдельное подтверждение.
6. Отчитайся: изменённые файлы, выполненные проверки, результат. Не утверждай, что проверка прошла, если команда не запускалась.

## Документация

- Новую норму добавляй в Rule.
- Новое определение поведения — в Spec через OpenSpec change.
- Карту текущего состояния — в Domain Profile.
- Процесс и навигацию — в `AGENTS.md` или связанную процедуру.
- Не дублируй содержимое: ссылайся на источник.
- Не выдавай текущие соглашения за неизменяемые инварианты.
- Не создавай отдельные профили для ролей или компонентов без обоснованной необходимости.
- Baseline Specs, созданные при миграции документации, допускаются как разовое исключение; дальнейшие изменения поведения — через OpenSpec change.

## Specs

- `openspec/specs/frontend/client-api-mapping/spec.md` — клиентский mapping серверных контрактов.
- SSE payload, имена событий, reconnect и гарантии доставки не специфицированы. Не объявляй текущую реализацию контрактом; сначала нужно решение на уровне backend Spec или отдельной integration Spec.
- Auth/session и chat UI Specs пока отсутствуют. Не создавай их без согласованных требований.
- Backend REST/SSE Spec остаётся каноническим для серверной стороны; frontend Specs не дублируют его, а ссылаются на него.

## Git

- Правила безопасных изменений и работы с git — `.agents/rules/development/conventions.md`.

## Известные пробелы документации

- Нет frontend Specs по auth/session и chat UI/SSE; SSE-контракт не определён в backend REST Spec.
- Frontend Spec требует `next`; текущий клиент всё ещё читает `nextToken`; переход — отдельная задача изменения клиента.
- Точные поля `ChatListItem`/`ChatDetails`, преобразование `createdAt`, клиентская обработка `ProblemDetail` и реализация создания чата требуют отдельных решений.
- Процедура проверки вынесена в `.agents/procedures/verification.md`; это процессная часть, не Rule. Отдельного test-style и CI нет.
- `README.md` — устаревшая генерация Angular CLI; источником истины не является.
